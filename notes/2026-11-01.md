# pdfdown: AcroForm support + invoice extraction — design (2026-11-01)

Status: draft for review. Nothing here is built yet.

Scope of this document: add (1) PDF form (AcroForm) field extraction and
(2) invoice extraction to `@d0paminedriven/pdfdown` and
`@d0paminedriven/pdfdown-ocr`, using the pdfluent-sdk crates as _reference
material only_. Office formats (docx/xlsx/pptx) are discussed at the end but
are explicitly out of scope for this design.

---

## 1. Intent and why

- **Forms.** Enumerate AcroForm fields per page (name, type, value, options,
  flags, widget rectangle) from Node, the same way text, images and
  annotations are reported today. Read-only: pdfdown parses form data and
  reports where each field sits; it never fills fields or reproduces the form
  UI. A natural gap in the current extraction surface and a prerequisite for
  several invoice/form workflows.
- **Invoices.** Turn an invoice PDF (digital or scanned) into structured JSON:
  vendor, customer, invoice id, dates, totals, tax breakdown, payment details,
  and line items, each with a confidence and the page/box it came from. This is
  the priority item: it will be used at work (TypeScript + Node) to replace a
  hacky cloud-OCR pipeline. **OCR stays Tesseract-only, exactly as today.** No
  cloud services are called at any point; everything runs in-process in the
  native addon.
- **Study, don't depend.** We are not adding pdfluent crates as dependencies.
  We studied their design to decide what a good API and model look like, and
  we implement our own code on top of `lopdf` + the existing module layout.

## 2. What the repo looks like today (for the builder)

- Single Rust crate `pdfdown` (edition 2024, `rustc 1.94.1`, uses let-chains),
  compiled to a Node addon with napi-rs 3. Cargo features: `ocr`
  (`tesseract-rs 0.4`, system libtesseract) and `render` (`pdfium-render 0.9.4`,
  dynamic libpdfium). Base package build is `--features render`; OCR package is
  `--features ocr,render` with `ocr/package.json`.
- `src/lib.rs` (napi surface: sync fns, `AsyncTask` impls, `PdfDown` class
  holding `Arc<Document>` + `Arc<Vec<u8>>`), `src/types.rs` (napi object types +
  `Raw*` thread-safe mirrors), `src/core/{document,images,meta,text,ocr,render}.rs`.
- Conventions already in place that new work must follow:
  - Every extraction has a sync fn, an `*Async` fn (libuv pool via `AsyncTask`),
    and `PdfDown` methods sharing the parsed `Document` via `Arc`.
  - Napi types that hold `Buffer` have a `Raw*` twin for the worker thread.
  - Rayon for per-page parallelism; OCR runs on a capped, cached pool.
  - Ava tests in `__test__/` (base) and `ocr/__test__/` (OCR), fixtures under
    `__test__/fixtures`. Rust unit tests live next to the code.
  - `--no-const-enum`: string enums land in `.d.ts` as union types.
- Known docs drift to fix alongside this work: `README.md` does not mention the
  `render` feature (`renderPagesAsync`, `capabilities()`, `RenderOptions`,
  `OcrOptions.render/renderDpi/pdfiumPath`, `TextSource.Rendered`).
- Version note: `Cargo.toml` says 0.9.9 while `package.json` says 0.10.0
  (`napi version` bumps only package.json). Not a blocker, just be aware.

## 3. Findings from pdfluent-sdk (reference study)

Cloned at depth 1 into the session scratchpad for reading; nothing copied.

### 3.1 Licensing — the hard constraint

Every crate we looked at (`pdf-forms`, `pdf-invoice`, `pdf-extract`, `pdf-ocr`,
`pdf-engine`, `docx-extract`, `xlsx-extract`, `pptx-extract`) is licensed
`AGPL-3.0-only OR LicenseRef-PDFluent-Commercial`. pdfdown is MIT.

Rules for this work:

- Read their code for _behaviour, API shape and edge cases_. Do not copy code,
  comments, test fixtures, or data tables from the repo into pdfdown.
- Implement from the ISO 32000 spec, lopdf's API, and our own reasoning. The
  AcroForm data model is a spec, not pdfluent IP; a clean implementation will
  look similar in shape because the spec dictates the shape.
- Public sample files (Factur-X/ZUGFeRD samples from the standards bodies) are
  fine for tests; pdfluent's `fixtures/*.pdf` are not.

### 3.2 `pdf-forms` (pdfluent-forms) — AcroForm engine

What it does: parses `/AcroForm` into an arena `FieldTree`, flattens to a
plain `FormFieldModel` per _logical_ field, fills values with a careful
writeback chain (regenerates appearance streams), regenerates appearances,
flattens forms.

Behaviours worth matching (all spec-derived):

- Inheritance: `/FT`, `/Ff`, `/V`, `/DV`, `/DA`, `/Q`, `/MaxLen` resolve up the
  `/Parent` chain; `/DA` and `/Q` fall back to the AcroForm dictionary.
- A _logical field_ is a node that resolves to a field type and has no named
  children. Unnamed kids with `/Rect` are widgets of their parent (radio
  groups = one field, N widgets).
- Button kind from flags: pushbutton bit 17, radio bit 16, else checkbox.
  Choice kind: combo bit 18 (+ edit bit 19), else list (+ multiselect bit 22).
  Text: multiline 13, password 14, fileselect 21, comb 25, richtext 26.
- Checkbox/radio on-state = first non-`Off` key of the widget's `/AP /N`;
  default `Yes` when absent. Checked = `/V` ≠ `Off` or any widget `/AS` ≠ `Off`.
- `/Opt` entries are either strings or `[export display]` pairs.
- Text strings (`/T`, `/TU`, `/V`, `/DV`) are PDF text strings: UTF-16BE BOM,
  UTF-8 BOM, else PDFDocEncoding. `/Name` bytes are _not_ text strings; decode
  as UTF-8 then Latin-1 fallback.
- Page index for a widget comes from scanning each page's `/Annots` (build the
  map once; lopdf's `get_object_page` is a linear scan per call).
- Guard `/Kids` recursion with a visited set and a depth cap (cycles exist in
  the wild).
  What we deliberately skip: everything that writes (filling, appearance-stream
  generation, flattening), plus `/CO` calculation order and XFA. pdfdown reads
  form data; see §5.

### 3.3 `pdf-invoice` — not what the name suggests

`pdf-invoice` is **not** an invoice parser. It is:

1. FDF / XFDF import-export of AcroForm field data.
2. A lightweight AcroForm→XML / XDP exporter.
3. **ZUGFeRD 2.3 / Factur-X 1.0** support: generate CII (UN/CEFACT
   Cross-Industry Invoice) XML, embed it as a PDF/A-3 associated file
   (`/AF` + `/Names/EmbeddedFiles`, `/AFRelationship`), extract it back, and
   validate EN 16931 business rules.

Implication: for the work use case (arbitrary vendor invoices, often scanned)
there is nothing in pdfluent that does heuristic field extraction. pdfluent's
heavy lifting for "understanding a page" is in `pdf-engine` (block model,
learned table/heading models, 500k lines incl. baked model weights) — a far
larger investment than we want.

What we _do_ take from `pdf-invoice`: the embedded-XML discovery path is
cheap, deterministic, and increasingly common in EU invoices. If a PDF carries
Factur-X/ZUGFeRD/XRechnung XML, we parse that and return it with confidence
1.0, bypassing heuristics entirely. Their `ZugferdInvoice` data model (seller,
buyer, line items, currency, tax basis/tax/grand total/due payable, payment
means/terms, buyer reference) also informed the shape of our invoice fields.

### 3.4 `pdf-extract` — positioned text

Their `TextBlock { text, page, bbox, font_name, font_size, is_bold, is_italic,
color, char_bounds, width_source }` and `PositionedChar` come from a content
stream interpreter tracking CTM (`cm`, `q`/`Q`), text matrix/line matrix
(`BT`/`ET`, `Tm`, `Td`, `TD`, `T*`, `TL`), text state (`Tf`, `Tc`, `Tw`, `Tz`,
`Ts`), and show operators (`Tj`, `TJ`, `'`, `"`), with glyph advances from
font `/Widths` (estimate 0.5 em when unavailable, flagged via `width_source`).

lopdf's built-in `Document::extract_text` gives us _only_ concatenated strings
(it inserts a space for `TJ` offsets < −100 and that is all). For invoices we
need x/y, so we build the interpreter ourselves (§6). lopdf gives us the
pieces: `Content::decode`, `get_page_content`, `get_page_fonts`,
`Dictionary::get_font_encoding`, `Encoding::bytes_to_string`.

### 3.5 `pdf-ocr` — word-level OCR

Their engine trait returns `OcrWord { text, bbox_px, confidence }` per word
and they get word boxes from Tesseract via hOCR (`leptess`) or the TSV output
of the CLI. We already link `tesseract-rs 0.4`, which exposes
`TesseractAPI::get_iterator() -> ResultIterator` with
`get_word_with_bounds() -> (text, x0, y0, x1, y1, conf)` and `next_word()`, plus
`get_tsv_text`/`get_hocr_text` as alternatives. So word boxes are a small
addition to `src/core/ocr.rs`, no new dependency.

### 3.6 `docx-extract`, `xlsx-extract`, `pptx-extract`

Zip + `quick-xml` (both MIT) parsers that map Office XML onto pdf-engine's
`Block/BlockKind` so everything serialises to one Markdown. Clean idea; not
PDF; not needed for forms or invoices. See §11.

## 4. Goals, non-goals, anti-goals

**Goals**

- G1. Read AcroForm fields per page with full fidelity for the common field
  kinds, from both packages, sync + async + class API, in the same flat
  page-tagged shape as images and annotations.
- G2. Positioned text (words + lines with boxes) for native pages, and for
  OCR'd pages in the OCR package, in one shared shape.
- G3. Invoice extraction that returns typed fields with confidence and
  provenance (page + box), from native text, from OCR, or from embedded
  e-invoice XML, with the same result shape regardless of source.
- G4. Keep both npm packages drop-in compatible: no existing API changes.
- G5. Pure-Rust additions in the base package (must still build for WASI);
  OCR-dependent parts live only in `pdfdown-ocr`.

**Non-goals (v1)**

- Writing to PDFs in any form: filling fields, appearance-stream generation,
  flattening, FDF/XFDF import/export, generating e-invoice XML. pdfdown
  extracts; it does not author or reproduce form UI.
- XFA forms, digital signature validation.
- Learned/ML layout models. Heuristics + geometry first; measure on a corpus;
  only then consider more.
- Receipts, purchase orders, bank statements as separate models. The invoice
  extractor will often work on them, but we don't tune for them.

**Anti-goals (things that would make this a failure even if it "works")**

- Any network call or cloud dependency in the extraction path.
- Copying AGPL code into an MIT package.
- Blocking the Node event loop by default for heavy paths (OCR, layout,
  invoice): async variants are mandatory, docs steer to them.
- A "magic" invoice result with no confidence/provenance. Every field must
  say how sure we are and where it came from so the consuming app can route
  low-confidence documents to review.

## 5. Feature A — AcroForm field extraction (read-only, per page)

### 5.1 Module and API

New module `src/core/forms.rs` (pure lopdf). New napi types in
`src/types.rs` (or a `src/types/` directory split — builder's call; `types.rs`
is already 328 lines and will roughly triple).

The API is 1:1 with what exists. `extractXPerPage` returns a flat array of
page-tagged items, `PdfDown.xPerPage()` mirrors it, `pdfDocument*` carries the
array plus `totalX` and `xPages`, and document-level facts live on `PdfMeta`.
Nothing is bolted on beside that pattern, and every `page` is a real 1-based
page number as everywhere else in the package.

Form fields are reported **per page, one entry per widget placement**, exactly
like `PageImage` and `PageAnnotation`. A logical field placed on several pages,
or a radio group with one widget per option, yields several entries that share
the same `fieldObjectId` and `name`. Widgets _are_ annotations
(`/Subtype /Widget`), so this is the granularity `extractAnnotationsPerPage`
already uses; those widget annotations keep appearing there unchanged, and
`formFields` adds the resolved form data on top.

Mixed documents are the norm, not the exception: a contract with one signature
page and twenty pages of prose, an application with a form on page 1 and
attachments behind it. Pages without widgets simply contribute no entries, and
`formFieldPages` names the pages that do, so a consumer can route form pages
and text pages differently without scanning the array (same idea as
`imagePages` / `annotationPages`).

```ts
export interface ChoiceOption {
  exportValue: string;
  displayValue: string;
}

// Emitted by napi-derive 3.7 from a Rust *structured enum* (an enum whose variants carry
// fields). The discriminant key defaults to "type"; the literal is the variant name.
// napi has no shared base type, so the common fields are written out in every variant.
export type PageFormField =
  | {
      type: "Text";
      /* common */ multiline: boolean;
      password: boolean;
      comb: boolean;
      richText: boolean;
      maxLen?: number;
    }
  | { type: "Checkbox"; /* common */ onState?: string; exportValue?: string; checked: boolean }
  | { type: "Radio"; /* common */ onState?: string; exportValue?: string; selected: boolean } // one entry per option widget
  | { type: "ComboBox"; /* common */ options: Array<ChoiceOption>; editable: boolean }
  | { type: "ListBox"; /* common */ options: Array<ChoiceOption>; multiSelect: boolean; values?: Array<string> }
  | { type: "PushButton" /* common */ }
  | { type: "Signature"; /* common */ signed: boolean } // signature data present in /V; NOT cryptographic validation
  | { type: "Unknown" /* common */ }; // widget annotations no field claims (orphans, or no /AcroForm at all)

// "common" on every variant:
//   page: number;           // 1-based, always a real page, like PageText / PageImage / PageAnnotation
//   rect: Array<number>;    // [x0, y0, x1, y1] PDF user space, same convention as PageAnnotation.rect
//   objectId: string;       // this widget's object id, "N G obj" like PageImage.objectId ("page P annot I" for an inline dict)
//   fieldObjectId: string;  // the logical field's object id; identical on every placement of one field
//   name: string;           // fully qualified "parent.kid"; unique per spec, but merged PDFs break that, so join on fieldObjectId
//   partialName: string; widgetIndex: number; widgetCount: number;   // placement i of n for this field (placed widgets only)
//   value?: string; defaultValue?: string; tooltip?: string; mappingName?: string;
//   readOnly: boolean; required: boolean; noExport: boolean; hasActions: boolean
// Presentation-only data (/DA font+colour, /Q alignment, /MK, appearance streams) is deliberately
// not surfaced: pdfdown reports field data and geometry, not how a viewer should draw it.
//
// Buttons keep the spec's two representations apart (ISO 32000-1 §12.7.4.2.3): `onState` is the
// appearance state name from this widget's /AP /N (absent, never invented, when the widget has no
// appearance dictionary); `exportValue` is the /Opt entry that state maps to when the field has
// /Opt, else the state name. `checked` / `selected` resolve in order: /AS when present; else /V
// equals this widget's state name; else, with no appearance states at all, a checkbox is checked
// iff /V is a non-Off name while a radio widget is reported unselected with a warning (a group value
// alone cannot identify a state-less widget; a one-widget group is treated like a checkbox). `value`
// always reports /V (in export-value form). The two can disagree (`checked: false`, `value: "Ja"`) and both
// are reported so stored data and appearance state stay distinguishable.

// Prepended from types/dts-header.ts (napi.dtsHeaderFile) together with Rm / XOR / CTR / RTC / UTR:
export type FormFieldType = PageFormField["type"];
export type FormFieldByType = UTR<PageFormField, "type", true>; // { Text: {...}, Checkbox: {...}, ... } minus the discriminant

// Document-level facts live where isLinearized / pageBoxes already live: `form?: FormInfo` on
// PdfMeta (pdfMetadata / metadata()) and flat on PdfDocument / PdfDocumentOcr. Present when
// /AcroForm exists or orphan widgets were found; absent otherwise, like `creator?`.
//
// A field with no placed widget keeps its whole logical payload; only geometry and per-widget
// state are absent. (A second discriminated union was considered and rejected for v1: unplaced
// fields are rare, and a flat record loses nothing a consumer can act on.)
export interface UnplacedFormField {
  fieldObjectId: string; // "N G obj"; synthesized "<parent fieldObjectId>/kid I" (or "/Fields I") only when the FIELD dictionary itself is inline
  name: string;
  partialName: string;
  type: FormFieldType;
  signed: boolean; // Signature fields: signature data present in /V (false for every other type)
  value?: string;
  values?: Array<string>; // multi-select list boxes
  defaultValue?: string;
  tooltip?: string;
  mappingName?: string;
  options?: Array<ChoiceOption>; // choice fields
  maxLen?: number;
  readOnly: boolean;
  required: boolean;
  noExport: boolean;
  hasActions: boolean;
  multiline: boolean;
  password: boolean;
  comb: boolean;
  richText: boolean;
  editable: boolean;
  multiSelect: boolean;
}
export interface FormInfo {
  hasAcroForm: boolean; // /AcroForm present (false when only orphan widgets were found)
  hasXfa: boolean; // /AcroForm /XFA present (we do not parse XFA)
  needAppearances: boolean;
  sigFlags: number;
  fieldCount: number; // logical fields, placed + unplaced; may differ from totalFormFields
  widgetCount: number; // placements; always equals totalFormFields and formFields.length
  unplacedFields: Array<UnplacedFormField>; // fields with no widget on any page: data kept, no geometry invented
  truncated: boolean; // the /Kids depth cap (100) was hit somewhere: the result is partial
  warnings: Array<string>; // dangling references, non-array /Annots, non-dictionary /Kids entries, depth cap: "nothing present" vs "could not extract"
}

export declare function extractFormFieldsPerPage(buffer: Buffer): Array<PageFormField>;
export declare function extractFormFieldsPerPageAsync(buffer: Buffer): Promise<Array<PageFormField>>;
// PdfDown: formFieldsPerPage(), formFieldsPerPageAsync()
// PdfDocument / PdfDocumentOcr gain formFields: Array<PageFormField>, totalFormFields: number, formFieldPages: Array<number>
```

Counts, stated once: `totalFormFields === formFields.length === form.widgetCount`.
`form.fieldCount` counts logical fields and is usually smaller (radio groups,
fields repeated across pages) or larger (unplaced fields); never assume
equality. `formFieldPages` is the sorted unique set of `page` values, always
present and empty when there are none, like `imagePages`.

Napi mapping notes: `PageFormField` carries no `Buffer`, so no `Raw*` twin is
needed; the structured enum crosses the `AsyncTask` boundary as-is.

### 5.1.1 How the union reaches `.d.ts` (no postbuild rewrite)

Two build-time mechanisms, both already in the installed toolchain:

1. **Structured enum in Rust.** `#[napi(object_from_js = false)] pub enum
   PageFormField { Text { … }, Checkbox { … }, … }` with struct-style variants.
   napi-derive 3.7 generates `ToNapiValue` (the discriminant is written as the
   first property) and the TypeScript union above; `Vec<PageFormField>` types
   as `Array<PageFormField>`. Rules the builder must respect:
   - **Named-field variants only.** Tuple variants come out as `field0`,
     `field1`, which is useless to a consumer. Even `PushButton` and `Unknown`
     carry the common fields, so no variant is a bare unit.
   - **No common field may be called `type`.** It is the discriminator; napi
     rejects the clash at compile time.
   - **Output only.** `object_from_js = false` skips the `FromNapiValue` side,
     since nothing ever passes a `PageFormField` back in. Less generated code,
     and no requirement that every field type be readable from JS.
   - `#[napi(discriminant = "…")]` renames the key and
     `discriminant_case = "camelCase"` recases the literals; we keep the
     defaults (`type`, PascalCase variant names) to match `TextSource` and
     `BoxType`, which are already PascalCase string unions.
   - `FormFieldType` is derived in the header as `PageFormField["type"]`, not a
     second Rust `string_enum`, so the literal set has one source of truth.
     The common fields repeat in each variant; a small `macro_rules!` stamps them
     so they are declared once in Rust. Bump `napi-derive` to `3.7` in
     `Cargo.toml` (the lock already resolves 3.7.0) so a fresh resolve cannot
     fall below the feature. `--no-const-enum` only affects unit enums; a
     structured enum emits `export type` regardless.
2. **`napi.dtsHeaderFile`** in _both_ `package.json` and `ocr/package.json` (the OCR build
   reads its own napi config; the path is relative to the repo root, so one shared file
   `types/dts-header.ts` serves both). The CLI prepends the file verbatim on every
   `napi build`, including `preversion` and the CI matrix, so nothing can ship un-augmented.
   It **replaces** the default header, so the file starts with
   `/* auto-generated by NAPI-RS */` and `/* eslint-disable */`, then the utility types
   (`Rm`, `Without`, `Include`, `XOR`, `CTR`, `RTC`, `IsExact`, `UTR`, `IsOptional`,
   `OnlyOptional`, `OnlyRequired`) and the derived aliases (`FormFieldType`,
   `FormFieldByType`). TypeScript hoists type aliases, so the header may reference
   `PageFormField` even though it is declared further down the file.

A postbuild rewrite script was considered and rejected: `napi build` runs from five places
(`build`, `build:debug`, `build:ocr`, `preversion`, CI) and each one regenerates
`index.d.ts`; a header in config is applied by the generator itself.

### 5.2 Reading — algorithm

1. Scan pages first, independent of `/AcroForm`: for every page, resolve
   `/Annots` (direct array or reference; lopdf's `get_page_annotations` handles
   both, but we walk the entries ourselves to keep each widget's `ObjectId`)
   and record every `/Subtype /Widget` as `ObjectId → (page, rect, index)`.
   Inline widget dictionaries get a synthesized `objectId` (`"page P annot I"`).
2. Read `/AcroForm` from the catalog if present: `/NeedAppearances`,
   `/SigFlags`, `/XFA` presence (`/DA` and `/Q` are presentation data and are
   skipped). Absent → `hasAcroForm: false`, and processing continues, because
   step 1 may still have found widgets.
3. Walk `/Fields` through `/Kids` with a visited `HashSet<ObjectId>` and a depth
   cap (100). Every entry (`/Kids`, `/V`, `/DV`, `/Opt`, `/AP`) is dereferenced
   through the document before it is read; a dangling reference counts as
   absent and adds a warning; hitting the depth cap sets `truncated` and adds a
   warning naming the field. Build nodes with the inheritable attributes (`/FT`,
   `/Ff`, `/V`, `/DV`, `/MaxLen`, `/Opt`) and `parent` links. Decode text
   strings with `lopdf::decode_text_string` (UTF-16BE BOM, UTF-8 BOM,
   PDFDocEncoding) and name bytes as UTF-8 then Latin-1.
4. Resolve logical fields: a node with an effective `/FT`, no child carrying a
   non-empty `/T`, and either a non-empty `/T` of its own or a place in the root
   `/Fields` array. An unnamed node with a parent is a widget of that parent,
   never a field of its own (so a radio group with three unnamed kids is one
   field). A merged field+widget dictionary (named, has `/Rect`, no kids) is one
   field with one placement. Derive `type`, flags, options, state names, export
   values and value(s) once per logical field; `fieldObjectId` is the terminal
   field dictionary's id. Field↔widget joins use object identity only. An
   inline `/Kids` dictionary (written directly into the array) can never match a
   page's `/Annots` entry: when it is an unnamed widget, its named parent is the
   logical field and is reported as unplaced under the parent's own
   `fieldObjectId`; when it is itself a named field (or an inline root `/Fields`
   entry), the field gets the synthesized id `"<parent fieldObjectId>/kid I"`
   (`"/Fields I"` at the root). An inline `/Annots` widget dictionary can never
   be claimed and is reported as `Unknown`. Documented limitation; all three
   cases are tested.
5. Emit one `PageFormField` per widget that step 1 placed on a page: `page`,
   `rect`, `objectId`, `fieldObjectId`, `widgetIndex` / `widgetCount` (placed
   widgets only), the shared field data, and per-widget button state
   (`onState` / `exportValue` from this widget's `/AP /N` and the field's `/Opt`;
   `checked` / `selected` from `/AS`, falling back to the group `/V`). Widgets
   from step 1 that no field claims become `Unknown` entries. Fields whose
   widgets were not found on any page go to `form.unplacedFields` with their
   full logical payload and no geometry.
6. Sort by `(page, -y0, x0, name)`. `formFieldPages` = sorted unique pages;
   `totalFormFields` = array length.

Parallelism: not needed; the field tree is tiny compared to page content.

### 5.3 Edge cases to test

Inherited `/FT` on a parent with unnamed kids; radio with 3 widgets and `/Opt`
export values (3 entries sharing `fieldObjectId` and `name`, exactly one
`selected`, `form.fieldCount` smaller than `totalFormFields`); checkbox with
on-state `Ja`; comb text with `/MaxLen`; multi-select list with `/I`; `/Opt`
pairs; UTF-16BE `/V` with umlauts; a field tree with a `/Kids` cycle; one field
with widgets on page 2 and page 3 (two entries, `widgetIndex` 0 and 1,
`widgetCount` 2); a field with no widget (appears only in `form.unplacedFields`,
never in the per-page array); two fields with the same fully-qualified name
(merged PDFs) distinguished by `fieldObjectId`; a PDF with Widget annotations
but no `/AcroForm` (`Unknown` entries, `form.hasAcroForm` false); AcroForm with
`/XFA` (report `hasXfa`, still read the AcroForm part); `/Annots` as an indirect
reference and as inline dictionaries; no AcroForm and no widgets (`form`
absent, empty array, empty `formFieldPages`); a form already filled by another
tool (values in `/V` and `/AS`) reads back the filled values; `/V` and `/Opt`
entries written as indirect references resolve like direct ones, and a dangling
reference yields no value plus a warning; an unnamed inline `/Kids` widget leaves its
named parent unplaced under the parent's own id, while an inline named field
dictionary gets a `/kid 0` id; an unplaced `/Sig` field with a `/V` dictionary
reports `signed: true`; a radio widget whose `/AP` state is `1` and
whose `/Opt` export is `Green` reports both; a checkbox with no `/AP` has no
`onState`; RC4-128 and AES-256 encrypted copies (empty user password) read the
same fields as the plaintext file; widget
annotations still present in `extractAnnotationsPerPage` output with
`subtype: "Widget"`; the field list cross-checked against `qpdf --json` on every
fixture.

## 6. Feature B — Layout: positioned words and lines

This is the foundation for invoices (and later tables/key-value in general).
It lives in the base package; OCR word boxes plug into the same shape.

### 6.1 Shape

```ts
export type TextSource = "Native" | "Ocr" | "Rendered"; // becomes unconditional (today ocr-only)

export interface TextWord {
  text: string;
```

### 6.2 Native interpreter (`src/core/layout/`)

- `interpreter.rs`: walk `Content::decode(page content)` operations with a
  graphics state stack (`q`/`Q`, `cm`), text object state (`BT`/`ET`, `Tm`,
  `Td`, `TD`, `T*`, `TL`, `Tc`, `Tw`, `Tz`, `Ts`, `Tf`) and show operators
  (`Tj`, `TJ`, `'`, `"`). For each shown string: decode bytes through the
  font's `Encoding` (lopdf `get_font_encoding` + `bytes_to_string`), advance
  the text matrix per glyph using glyph widths, and emit glyph boxes
  `[x, y + descent, x + adv, y + ascent]` transformed by `Tm × CTM`.
- `fonts.rs`: per-page font cache keyed by resource name: encoding, glyph
  widths (`/FirstChar` + `/Widths` for simple fonts; `/W` + `/DW` for
  CIDFontType0/2 under Type0, keyed by CID; `/MissingWidth` from the
  descriptor), ascent/descent from `/FontDescriptor` (fallback 0.9/−0.2 em),
  `bold`/`italic` inferred from the descriptor flags/weight and the base font
  name. Type3: use `/FontMatrix` and `/Widths`. Width source flagged
  (`Metric`/`Estimate`) internally; estimate = 0.5 em.
- Form XObjects: on `Do` of a `/Form`, recurse with `CTM × /Matrix`, using the
  form's own `/Resources` (fallback to page resources), with a depth cap.
  Image XObjects on `Do`: record the unit square under the CTM as a
  `PlacedImage` (needed to map OCR pixel boxes for embedded scans, §6.3).
- Reuse `core::images::get_inherited_resources` / page content helpers rather
  than duplicating; promote them to `pub(crate)` as needed.
- Robustness: malformed operands never panic (`as_float().ok()` everywhere),
  content decode errors degrade to an empty page, decompression bombs are
  bounded with `get_page_content_with_limit` (**call:** 64 MiB per page).

`words.rs`:

- Group glyph boxes into words: split at explicit space glyphs, at `Tw`
  adjustments, at `TJ` negative offsets large relative to font size, and at
  gaps > 0.25 em between consecutive glyph boxes on the same baseline.
- Lines: cluster words whose baselines differ by < 0.5 × median glyph height
  and whose vertical overlap > 50%; sort by x; join with single spaces.
- Order lines top→bottom, left→right. Rotated text (non-axis-aligned `Tm×CTM`)
  is kept with its true bbox and simply participates in clustering (no special
  handling in v1).
- Right-to-left scripts: no bidi handling in v1 (same stance as pdfluent).

Rayon per page, same as `extract_text`.

### 6.3 OCR words (`src/core/ocr.rs`, `ocr` feature)

- Add `ocr_words(img: &DynamicImage, lang, dpi_hint) -> Vec<OcrWordPx>`: after
  `set_image`, call `set_source_resolution(dpi)`, `recognize()`, then iterate
  `get_iterator()` with `get_word_with_bounds()` / `next_word()`; keep words
  with non-empty trimmed text; confidence = Tesseract word conf / 100.
- Pixel → PDF points:
  - Tier 3 (rendered page at `dpi`): `x_pt = px × 72 / dpi`,
    `y_pt = page_height − py × 72 / dpi` (flip, y up).
  - Tier 2 (embedded image XObject): use the `PlacedImage` box recorded by the
    native interpreter for that XObject: scale pixel coords into the placed
    rectangle (flip y). If the image is painted more than once or the box is
    missing, fall back to scaling into the page box and add a per-page warning.
- Lines: Tesseract's own line grouping (iterate `RIL_TEXTLINE`) is used when
  available, else fall back to the same clustering as native.
- The existing text cascade (native → embedded-image OCR → render+OCR) and
  `TextSource` tagging are reused unchanged; `layoutWithOcrPerPage` is the
  cascade with words instead of a string.

### 7.2 Track 1 — embedded e-invoice XML (`src/core/attachments.rs`, `src/core/invoice/einvoice.rs`)

- Generic attachments API: walk `/Names /EmbeddedFiles` (name tree with
  `/Names` and `/Kids`), the catalog `/AF` array, and page-level
  `/FileAttachment` annotations. Return
  `Attachment { name, mimeType?, size, relationship?, description?, data: Buffer }`
  (decompressed via `Stream::decompressed_content`, bounded).
- E-invoice detection: candidate when `relationship ∈ {Data, Alternative,
  Source}` or filename ∈ {`factur-x.xml`, `zugferd-invoice.xml`,
  `ZUGFeRD-invoice.xml`, `xrechnung.xml`} or XMP `fx:DocumentFileName` names
  it. Sniff the root element: `rsm:CrossIndustryInvoice` → CII
  (Factur-X / ZUGFeRD; profile from `GuidelineSpecifiedDocumentContextParameter/ID`,
  XRechnung when the URN contains `xrechnung`); `ubl:Invoice` /
  `ubl:CreditNote` → UBL.
- Parse CII (and UBL, best effort) with `roxmltree` (MIT/Apache, pure Rust,
  WASI-safe) into `InvoiceFields` with confidence 1.0 and no spans. Map:
  seller/buyer → vendor/customer (+ addresses, VAT ids), `ExchangedDocument/ID`
  → invoiceId, `IssueDateTime` (format 102, YYYYMMDD) → invoiceDate,
  `DueDateDateTime` → dueDate, `BuyerOrderReferencedDocument` → purchaseOrder,
  monetary summation → subTotal/totalTax/invoiceTotal/amountDue, applicable
  trade tax → taxDetails, payment means IBAN/BIC → paymentDetails, line items
  → items. Document type code 380 → Invoice, 381 → CreditNote.
- If `preferEmbeddedXml` and parse succeeds: `source: 'EmbeddedXml'`, done.
  We still return `warnings` if the PDF's text totals disagree with the XML
  (cheap cross-check, optional).

### 7.3 Track 2 — heuristic extraction from layout (`src/core/invoice/`)

Input: `Vec<PageLayout>` (native, OCR, or per-page mixed → `source: 'Mixed'`).

`lexicon.rs` — label vocabulary per language. English v1 covers at least:
invoice number/no./#/id, invoice date/date of issue/issued, due date/payment
due/pay by, purchase order/PO/P.O. number, bill to/invoice to/customer/sold to,
ship to/deliver to, remit to/pay to, subtotal/sub-total/net, tax/VAT/GST/HST/
sales tax, total/grand total/invoice total/total due, amount due/balance due,
terms/payment terms/net 30, account/IBAN/BIC/SWIFT/routing/ABA, VAT ID/Tax ID/
EIN/ABN. Matching is case-insensitive, punctuation-insensitive, tolerant of
OCR confusables (`0/O`, `1/l/I`) via a normalised form, and scored (exact >
prefix > fuzzy ≤ 1 edit per 5 chars). The table design allows adding `de`,
`fr`, `nl`, `es` later without touching the engine.

`dates.rs` — parse ISO, `MM/DD/YYYY`, `DD/MM/YYYY`, `DD.MM.YYYY`,
`YYYY/MM/DD`, `Nov 1, 2026`, `1 Nov 2026`, `November 1st, 2026`,
`01-Nov-26`. `Auto` order: if any date on the page is unambiguous (day > 12)
infer the order and apply to the rest; else prefer MDY when `languages`
starts with `en` and currency is USD, DMY otherwise.

`amounts.rs` — tokens like `$1,234.56`, `1.234,56 €`, `EUR 1 234,56`,
`(123.45)` (negative), `-123.45`, `123.45-`, `USD`, `CAD$`, `£`, `€`, `CHF`.
Separator inference per document: if `Auto`, the separator that is followed
by exactly 2 digits at the end of the token is decimal; majority vote across
the page. Currency symbol → code mapping with `opts.currency` tie-breaker.

`identifiers.rs` — invoice id (alphanumeric with digits, 3–30 chars,
label-anchored), PO number, VAT ids (EU country prefix + pattern), US EIN
(`NN-NNNNNNN`), IBAN (format + mod-97 check), BIC/SWIFT (8/11 chars),
email, phone, URL.

`anchors.rs` — key-value geometry. For each lexicon hit (label line or label
words), candidate values are: the remainder of the same line to the right of
the label (after a `:` if present), the nearest line below whose x0 is within
1.5 em of the label x0, and the nearest line to the right on the same baseline
in an adjacent column. Each candidate gets a geometry score, a type-validator
score (does it parse as a date/amount/id?), and the label match score.
Candidates are ranked; ties favour same-line-right, then below.

`parties.rs` — vendor: the top 25% of page 1; prefer the largest font line
that is not a lexicon label and not a date/amount, else the first text block;
the vendor address block is the run of 1–5 lines directly under it until a
blank gap or a label. Customer/bill-to/ship-to/remit-to: anchor on the label,
take the block of lines below until a blank gap, another label, or a numeric
line. First line of a block = name, the rest = address lines; any VAT/email/
phone found inside is pulled out into its own field.

`tables.rs` — line items.

1. Header row: a line containing ≥ 2 column keywords (description/item/
   details, qty/quantity, unit/uom, unit price/rate/price, amount/total/
   line total, tax/vat, code/sku/part no., date).
2. Column bands: x-ranges from the header words, widened to midpoints
   between neighbours; numeric columns right-aligned by convention.
3. Body: lines between the header and the first totals-region label
   (subtotal/total/amount due) or the page bottom; continue across pages when
   the next page has the same header. Assign each word to the band with the
   greatest x-overlap of its centre.
4. Rows: a line with a parseable amount in the amount band starts a row;
   lines with text only in the description band are merged into the previous
   row's description (multi-line descriptions).
5. Validate: `qty × unitPrice ≈ amount` (tolerance 0.01 or 0.5% for rounding)
   boosts the row; `Σ amount ≈ subTotal` boosts the whole table.
6. If no header is found but a right-aligned column of amounts exists above
   the totals region, emit rows with `description` + `amount` only at lower
   confidence.

`totals.rs` — reconciliation: among candidates for subTotal, totalTax,
totalDiscount, shippingCost, invoiceTotal, amountDue pick the combination
where `subTotal − discount + tax + shipping ≈ invoiceTotal` and
`amountDue ≈ invoiceTotal − previousPayments` within tolerance; a successful
reconciliation adds +0.2 confidence (capped at 0.99) to each participating
field and resolves "Total" ambiguity (the largest amount near the bottom
labelled total is the invoice total; the tax line is the one whose value ≈
rate × base when a `%` is visible).

`mod.rs` — orchestration: detect embedded XML first; else run the pipeline;
fill `confidence` per field as `0.5·label + 0.3·validator + 0.2·geometry`
(each 0..1) multiplied by the mean OCR word confidence of the span when the
page came from OCR; document confidence = weighted mean over
{invoiceId, invoiceDate, vendorName, invoiceTotal, amountDue} + reconciliation
bonus. `documentType` = CreditNote when "credit note"/"credit memo" appears in
the top 25% or totals are negative.

Parallelism: pages are already parallel in layout; the invoice pass is
per-document and fast (string/geometry work). It runs inside the same
`AsyncTask`.

### 7.5 Scale: very long invoices

The work corpus includes an 896-page invoice that takes a person about three
business days to work through by hand. It is the extreme case, but it carries
real billable hours, so "hundreds of pages of line items" is a first-class
input, not an edge case:

- **Chunking.** `layoutPerPage*`, `layoutWithOcrPerPage*`, `extractInvoice*`
  and `extractInvoiceWithOcr*` accept `pages?: PageRange` (1-based, inclusive)
  so a job runner can process a long document in slices and merge the per-page
  results; the per-page shapes make merging trivial. Invoice extraction over a
  slice returns the line items of that slice and leaves header fields whose
  pages are outside the slice `undefined`.
- **Cancellation.** Every new `*Async` entry point takes an optional
  `AbortSignal` (napi `AsyncTask::with_signal`); the per-page loops check it
  between pages. OCR of 896 scanned pages at 1–3 s per page on four threads is
  5–20 minutes, and callers must be able to stop it.
- **Bounded memory.** Pages are independent; at most `maxThreads` rendered
  pages exist at once (already true of the OCR cascade). Layout words never
  cross into JS unless `includeLayout` is set; the invoice engine consumes them
  in Rust. `pdfDocument*` on such a file is the consumer's choice (its `images`
  payload alone can be gigabytes) and the README says so.
- **Cross-page tables.** The header row may repeat on every page, appear once
  on the first detail page, or be absent on continuation pages; column bands
  persist from the last header seen until a totals region or a different
  header appears. Page-local lines (`Page N of M`, `Continued`, `Carried
  forward`, `Subtotal this page`, `Balance brought forward`) are recognised,
  excluded from `items`, and kept as `pageSummaries[].pageTotal`. A multi-line
  description may straddle a page break.
- **Summary versus detail.** Document totals are taken from a summary region
  (first or last pages; labels `Total`, `Amount Due`, `Invoice Total`) and the
  sum of `items` is reconciled against them with a tolerance that scales with
  row count (`max(0.01, 0.005 × rows)`); section subtotals (per account, cost
  centre, service) are reconciled when their labels are present. A failed
  reconciliation is a warning carrying the delta, never a silent acceptance.
- **Coverage report.** `InvoiceResult.pageSummaries` tells a reviewer which of
  the 896 pages contributed rows, which contained money-like tokens no row
  claimed, and which came from OCR at low confidence. That is what turns three
  days of reading into a review of the flagged pages.
- **Performance budget.** Native layout of ~900 pages should finish in
  seconds (per-page parallelism, no per-word JS allocation unless requested);
  the invoice pass is linear in words. Phase 3 adds a `benchmark/` entry over a
  generated 900-page synthetic invoice, and over the real file when it is
  available locally (it is never committed).

  shared. If wanted, a sibling package (e.g. `@d0paminedriven/officedown`) or
  a separate crate in this repo turned into a Cargo workspace. Worth doing
  only if work needs it; it is independent of forms/invoices.
- Writing to forms at all (filling `/V`, appearance streams, flattening). Out
  of pdfdown's remit: it extracts, it does not author PDFs.
- FDF/XFDF export of form data (trivial once `formFields` exists; JSON covers
  the work use case).
- Generic key-value and table extraction APIs exposed on their own (the
  invoice engine's `anchors.rs` and `tables.rs` are built so this is a thin
  wrapper later).
- Non-English lexicons, bidi text, rotated page normalisation.

## 12. Decisions I'd like from you (defaults stated; none block phase 1)

1. **Fill in v1?** **Answered 2026-11-02: no.** Forms are read-only and
   reported per page like text, images and annotations. pdfdown parses the data
   (with widget geometry as metadata) and never recreates form UI. Filling and
   all appearance work are removed from the design.
2. **Field naming parity** with the cloud invoice model you are replacing
   (§7.1). Default: yes, camelCase versions of those names. Say so if you'd
   rather pick names from scratch.
3. **Locales.** Default: English labels; US and EU number/date formats both
   parsed, order auto-detected. Tell me if work invoices are US-only (then
   `dateOrder` defaults to MDY and we skip DMY inference) or if DE/FR/NL/ES
   labels matter soon.
4. **Acceptance bar for phase 4.** Default target on your private corpus:
   ≥ 95% exact match on invoiceId/invoiceDate/invoiceTotal/amountDue for
   native PDFs, ≥ 85% for scans, with calibrated confidence (fields reported
   ≥ 0.8 confidence are right ≥ 95% of the time). Plus the 896-page invoice:
   completes in one async call inside a normal worker's memory, every line item
   carries page provenance, the item sum reconciles to the summary total, and
   `pageSummaries` flags the pages that still need eyes. Adjust to what the
   work pipeline needs.
5. **Multi-invoice PDFs** (several invoices in one file). Default: out of
   scope; one invoice per document, multi-page allowed.
6. **Release cadence.** Default: 0.11.0 after phases 1–3, 0.12.0 after 4.

## 13. Calls I made (so you can veto quickly)

- Everything stays in the one crate behind feature flags; no workspace split.
- Long documents are handled with page-range chunking (`pages`) and
  `AbortSignal` cancellation on the async entry points, not with streaming APIs.
- Buttons report `onState` (appearance state name) and `exportValue` (`/Opt`
  mapping) separately; neither is invented when `/AP` is missing.
- Field↔widget joins are by object identity; an inline `/Kids` widget leaves
  its named parent unplaced under the parent's id, an inline field dictionary
  gets a synthesized id, inline `/Annots` widgets are `Unknown`.
- `FormInfo.truncated` / `FormInfo.warnings` make partial extraction visible.
- The WASI loaders and generated typings are produced by a local
  `yarn build --target wasm32-wasip1-threads` and committed; CI builds the wasm
  binary but does not emit those files (known workaround).
- `PageFormField` is a napi structured enum (native discriminated union, key `type`);
  utility types ride in via `napi.dtsHeaderFile`, not a postbuild rewrite.
- Pure-lopdf forms implementation; pdfium is never required for forms.
- Forms expose data + geometry only: no `quadding`, `/DA`, `/MK` or appearance info.
- Form fields are emitted per widget placement with a real 1-based `page` and
  `rect`, the same granularity as `PageAnnotation`; there is no `page: 0`.
  Fields without a placed widget live in `form.unplacedFields`.
- Placements are joined by `fieldObjectId` (object identity), with `name` kept
  for the fully-qualified field name; `objectId` identifies the widget, in the
  same `"N G obj"` format as `PageImage.objectId`.
- `FormInfo` rides on `PdfMeta` / `PdfDocument` like `isLinearized`, not a new
  top-level function.
- Widget annotations keep appearing in `extractAnnotationsPerPage` unchanged.
- `TextSource` exported in the base build too (additive).
- `roxmltree` + `regex` as the only new dependencies.
- Money as `number` + exact `text`, no minor-units field.
- No bidi, no rotation normalisation, English lexicon only, in v1.
- Fixtures generated by our own lopdf-based generator; pdfluent fixtures and
  code are never copied (AGPL).
