  after all, if only as extra evidence.
- **Not everything is a PDF.** One spreadsheet in 337 files is enough to make
  intake format detection part of the work pipeline. Office extraction stays
  out of pdfdown's scope for now (design §11) but the pipeline needs a branch
  for it.

### 1.2 The downstream contract

`ocr/__test__/private/shape.md` documents the wire format the existing Azure
pipeline posts to the accounts-payable system, and
`ocr/__test__/private/real-ams-payload-post-processing.md` holds one real
post-processed payload for one invoice. Both stay private; what matters for the
design is the split between **extraction** and **post-processing**:

| Needed on the wire                                                                                                                                                                                           | Source                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invoice number, date, gross amount, PO number, ship-to block, invoice vs credit, line items (part number, name, description, quantity, unit price, amount, serials, condition)                               | **Extraction**: already the vocabulary of `InvoiceFields` / `InvoiceItem` in design §7.1; `develop` adds `workOrder` and `aircraft[]` (model, MSN, registration, engine model, ESN) |
| Vendor id (from a vendor master), cost-bucket routing (material / labor / misc), category id, rental type, list vs discount price, created timestamp, dropping zero-total lines, a 0–100 advisory confidence | **Post-processing at work**: business classification over the extracted fields; not pdfdown's job                                                                                   |

So pdfdown's deliverable for the POC is a faithful, confidence-tagged
`InvoiceResult`; a thin TypeScript mapper at work turns that into the wire
payload. The mapper is also where the design's 0..1 confidence becomes the
contract's 0–100 score.

## 4. What the corpus tells phase IV

- **Template concentration first.** Measure per producer family. If the iText
  family and the Qt family parse well, most of the corpus is covered; the long
  tail (Crystal, SAP, PDF24, Microsoft Print To PDF) is where label-lexicon
  breadth matters.
- **Five-page documents**: find out whether pages 2–5 are terms/attachments.
  If so, header fields live on page 1 and the totals region must not be
  confused by boilerplate amounts on later pages. `pageSummaries` (design §7.5)
  is the tool for seeing that.
- **The 111-page invoice** is the local stand-in for §7.5: cross-page tables,
  carried-forward lines, reconciliation tolerance scaled by row count.
- **Scans (5)**: the OCR path must be measured separately; the `develop` note's
  OpenMP finding (library OCR ~8 s/page vs ~0.6 s/page with
  `OMP_THREAD_LIMIT=1`) is the first thing to fix before timing anything.
- **Aviation fields** (`aircraft[]`, `workOrder`) are not generic invoice
  vocabulary; they stay in `InvoiceFields` because this corpus needs them, and
  the lexicon work for them is phase IV scope.
- **Confidence calibration** matters more than usual: the downstream score is
  advisory and gates manual review. The §12 target (fields reported ≥ 0.8 are
  right ≥ 95% of the time) is the thing to measure on this corpus.

### Engine findings from the 2026-11-03 port review (phase IV tickets)

- **Per-image rotation vs per-page `contentRotation`.** `ocr_page_image_words`
  detects the upright turn per image and the page reports the last one; words
  are mapped through each image's own `upright_dest` (placement as painted, or
  turned about its corner). A page whose images disagree, or whose image is
  painted away from the origin, has words outside the reported `width`×`height`
  (seen on one scanned invoice in the private corpus). Fix: rotate every
  image's word boxes into one page frame, or report rotation per `PlacedImage`.
- **Tier-3 render anisotropy on `/Rotate 90|270` pages.** `render_page_words`
  maps PDFium's raster onto the unrotated `geo.bbox`, but PDFium sizes the
  raster after `/Rotate`, so x and y scale factors differ when the displayed
  text already reads upright. Fix: swap the bbox dimensions when `geo.rotate`
  is a quarter turn.

## 6. Evaluation harness for the POC

- **Reference data**: export the Azure pipeline's post-processed payload for
  every id in the corpus into the private directory as
  `<id>.expected.json` (one such file exists). Those are post-processed, so
  the comparison runs through the same thin mapper the real integration would
  use: `InvoiceResult` → wire shape → compare.
- **Metric**: per-field exact match for header fields; for line items,
  matching on (part number or description, amount) with precision/recall per
  document; totals reconciliation rate; confidence calibration (accuracy of
  fields reported above 0.8). Report per producer family and for the scanned
  subset separately.
- **Where it lives**: `scripts/invoice-eval.ts` as in design §9, reading
  `$PDFDOWN_INVOICE_CORPUS` (or the gitignored directory) and printing a
  table; results are never committed.
- **Baselines**: the Azure pipeline's own agreement with human-verified
  values, if any such verification exists; otherwise the POC compares two
  automated systems and disagreements need a human sample.
