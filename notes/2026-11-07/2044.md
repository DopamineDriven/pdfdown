# 2026-11-07 20:44 — OCR tuning pipeline

Design for measuring and tuning the OCR path on the private corpus: a fixed scanned sample, a
hand-checked labelled subset, label-free proxies over every scan, one command per run and one
to diff two runs. Brainstormed with Andrew on 2026-11-07; open for Andrew: the labelling flow and the JBIG2
route (§9). Builder check done (§10); knob results in §7.

## 1. Intent

About 16% of the corpus is scanned (983 scanned + 155 mixed of 6,949 PDFs on 2026-11-07), and
the two oldest id-prefix groups (2012–2016) are a third scans each. Today nothing measures how
well Tesseract reads them: the acceptance spec counts whether a field was read, not whether it
was read right. Every knob (thresholding, upscaling, page segmentation) and every alternative
engine (PaddleOCR through ONNX Runtime) is a guess until a number says otherwise. The pipeline
turns "Tesseract's success rate ain't it" into a measurement, then into a comparison.

## 2. Goals

- One command runs the OCR build over the scanned sample with a named configuration and
  prints the labelled accuracy per field on the hand-checked subset, the label-free proxies on
  the whole sample, and seconds per document.
- One command diffs two runs and lists the documents that flipped per field.
- The hand-checked subset is cheap to produce (pre-filled, confirm-or-correct) and lives as
  expected files beside the PDFs in the vocabulary the eval harness already reads.
- Every knob under test is a public option on the OCR methods, so the benchmark and a consumer
  tune the same surface.

## 3. Non-goals and anti-goals

- Not a second engine yet. The PaddleOCR/ort engine is its own design once the trait exists
  (§6.6); this pipeline is what makes that comparison a number.
- Not a GUI product. Whatever labelling aid is built is a local file in the private directory.
- Anti-goal: anything from the private corpus (values, filenames, vendor names, page images)
  entering a tracked file. Reports, labels, result files and sample lists stay under the
  gitignored private directory. Aggregates only in logs and notes.
- Anti-goal: tuning to the labelled 100. The proxies over all scans are the guard against it.

## 4. Constraints

- Tesseract 5.5.1 + Leptonica 1.82 as installed (system libraries, `use-system-tesseract`).
  Its `thresholding_method` variable (0 Otsu, 1 Leptonica adaptive Otsu, 2 Sauvola) is
  available without new code.
- The private spec and the scripts under `scripts/lib` are the foundation: `discoverCorpus`,
  the expected-file reader, the metrics, `yarn invoice:eval` with `PDFDOWN_EVAL_BUILD=ocr`.
  The index `report.json` (one row per document with `kind`) and the per-document
  `results/<id>.json` files exist as of commit 5a7c474.
- A full OCR pass over the ~1,100 scanned and mixed documents takes 15–25 minutes on the
  libuv pool at six concurrent documents (median 6 s, mean 8 s per document today). The
  sample must therefore be a subset for iteration and the full set for confirmation.
- Andrew's own files are not touched: `ocr/__test__/testing.ts`, his
  `ocr/__test__/private-corpus.spec.ts`, the fetch script.

## 5. Facts the design rests on (2026-11-07)

Corpus kinds: native 5,807 · scanned 983 · mixed 155 · empty 4 (6,949 PDFs).

Scans are made of: CCITT fax 70% of image pages, JPEG 29%, a few Flate and JPX; about half
paint at 150–249 dpi (200-dpi fax), half at 250–349. Most are single pages.

**JBIG2 is a decoding gap, not an OCR one.** 163 of 1,138 scanned/mixed documents (14%)
contain JBIG2 streams and 79 have no decodable raster at all. The cascade's render tier
(PDFium, tier 3) exists for exactly these pages, but PDFium is not found by autodetection on
this machine (`capabilities: render=false` in the OCR suite), so the baseline below ran
without it and those pages read as nothing. Two routes: make PDFium reachable at runtime
(`PDFIUM_LIBRARY_PATH`; measured as the `pdfium` configuration in §7) or decode JBIG2 in
Rust with `hayro-jbig2` (pure Rust, MIT/Apache-2.0, same family as the `hayro-jpeg2000`
decoder already in use), which keeps scans readable without a PDFium deployment. Andrew
decides the route (§9); until it lands, JBIG2-only documents stay out of the dev sample and
are reported as "no result" in the population proxies (my call).

Baseline, Tesseract as shipped (Otsu, no upscaling, default page segmentation), over the 321
scanned and mixed documents of the group pulled on 2026-11-07, label-free:

| proxy | value |
|---|---|
| id read | 57.3% |
| date read | 55.8% |
| total read | 63.6% |
| vendor read | 90.7% |
| reconciled to the cent | 24.3% |
| mean confidence | 0.73 |
| median / mean seconds per document | 6.0 / 8.0 |
| documents with no result (all JBIG2) | 24 |

"Reconciled to the cent" (subtotal plus tax equals total) only holds when every digit was
read right, so it is the one proxy that measures OCR accuracy without labels.

## 6. Decisions

### 6.1 The sample (Andrew: "13% is more than a sufficient sample")

The scanned and mixed rows of the index are the population. A deterministic, seeded pick of
100 stratified by raster resolution band, codec, page-count band and label language is the
**dev sample**; the full population is the **confirmation run**. The pick is a list of ids in
the private directory (`bench/sample.json`), regenerated only on purpose. Label language is
not a key: it is unknown before an OCR pass (my call, after the builder check); the three
keys above come from `rasters` in the per-document result files.

### 6.2 Truth (Andrew: "I can use my eyes to sift through ~100")

For the dev sample, an expected file beside each PDF in the `InvoiceFields` vocabulary the
eval harness reads, pre-filled with the current reading so the work is confirm-or-correct.
Fields labelled: invoice id, invoice date, invoice total, sub total, total tax, vendor name.
Three states per field (my call, after the builder check): a value means "must match"; `null`
means "absent from the document", so a value read there is a false positive and scores 0; an
omitted key means "unknown / not checked" and is not scored. `parseExpected` today warns on
`null`; it changes to read it as "absent". `subTotal` and `totalTax` join the scored header
fields in `scripts/lib/metrics.ts`, which adds two rows to `yarn invoice:eval` output.

### 6.3 Proxies over the whole population

Per run: fields read (presence), reconciled to the cent, mean OCR word confidence, documents
with no result, seconds per document. (Validator pass rates were dropped after the builder
check: every emitted field has already passed its validator, so the rate is 100% by
construction.) Reported per kind (scanned,
mixed) and per resolution band, because the knobs act differently on 200-dpi fax and 300-dpi
scans.

### 6.4 Runs and diffs

`yarn ocr:bench --config <name>` runs the OCR build over the dev sample (or `--full`), writes
`bench/runs/<timestamp>-<config>.json` with one row per document (id, kind, resolution band,
fields read, reconciled, confidence, ms, the engine and configuration, the commit hash and a
dirty-tree flag so a diff can tell a knob change from a parser change), and prints the
labelled accuracy and the proxies. `yarn ocr:bench:diff <run-a> <run-b>` prints the aggregate
deltas and the ids that flipped per field. Rows carry the six-digit id so a flip is one file
away.

### 6.5 Knobs are public options (my call)

The existing `OcrOptions` (`lang`, `render`, `renderDpi`, `maxThreads`, `minTextLength`,
`pdfiumPath`) gains `thresholding?: "otsu" | "adaptiveOtsu" | "sauvola"`, `minimumPpi?:
number` and `pageSegmentation?: "auto" | "block" | "column" | "sparse"`. No new type and no
`languages` field: the Tesseract model stays `lang` in its own `eng+spa` form, and the label
lexicons stay `InvoiceOptions.languages`; they are different axes. Defaults are today's
behaviour until a run says otherwise; the bench passes them through. The environment-variable
switches used for the 2026-11-07 experiment are a spike and are discarded.

### 6.6 Engine seam (my call, scope only)

An `OcrEngine` trait inside the OCR crate (raster in; words with boxes and confidences out),
Tesseract as the first implementation. The bench's run rows name the engine. The PaddleOCR/ort
implementation is a separate design; this one only leaves the seam.

The seam already exists on the TypeScript side: `invoiceFromLayout(pages)` takes any
`PageLayout[]`, and `scripts/lib/azure-layout.ts` (2026-11-08) maps an Azure Document
Intelligence read result onto pages, regrouping Azure's text regions into baseline lines, so
the reader runs on another engine's OCR with no Rust change (`yarn invoice:from-azure
<result.json>`). That is also how a PaddleOCR line output will be adapted, and how Azure reads
can serve as the reference transcription for the labelled set (§6.2): the eye-check shrinks
to the places where Azure and Tesseract disagree.

### 6.7 Acceptance floors

The private spec keeps its presence floors. The bench is a tool, not a gate, until labels
exist for the dev sample; then its labelled accuracy becomes a floor in the private spec.

## 7. Knob results (2026-11-07 spike)

Same 321 documents, same build (commit 775dbd0 plus the environment-gated spike), one knob at
a time, label-free proxies. "Baseline" here is Tesseract as shipped on that build; it differs
from §5 only by the parser work that landed in between.

| configuration | id | date | total | subtotal | reconciled | confidence | median s/doc | no result |
|---|---|---|---|---|---|---|---|---|
| baseline (Otsu, PSM default = single block) | 58.3% | 55.8% | 64.5% | 27.1% | 25.9% | 0.742 | 6.2 | 24 |
| thresholding Sauvola | 57.9% | 53.9% | 65.1% | 25.9% | 24.6% | 0.743 | 6.5 | 26 |
| thresholding adaptive Otsu | 55.5% | 58.6% | 62.3% | 25.2% | 24.9% | 0.740 | 7.6 | 24 |
| upscale rasters under 300 dpi to 300 | 58.6% | 59.2% | 66.0% | 26.5% | 24.6% | 0.741 | 9.3 | 24 |
| page segmentation auto (PSM 3) | 59.5% | 57.3% | 64.8% | 26.5% | 24.6% | 0.744 | 4.7 | 26 |
| **page segmentation sparse (PSM 11)** | **67.3%** | **65.1%** | 66.0% | **32.7%** | **32.4%** | **0.762** | **5.2** | 25 |
| `PDFIUM_LIBRARY_PATH` set (render tier) | 58.3% | 55.8% | 64.5% | 27.1% | 25.9% | 0.742 | 6.4 | 24 |

What it says:

- **Page segmentation is the knob.** Tesseract's API default is "single uniform block of
  text", which is wrong for an invoice (sparse labels and values in columns). Sparse text
  lifts every proxy at once, including the only one that measures digit accuracy
  (reconciled to the cent, +6.5 points, 27 documents gained against 6 lost), and it is
  faster. Auto layout analysis is neutral. The per-document diff shows sparse also loses 13
  ids and 16 dates that the block mode read, so the cascade should try sparse first and fall
  back to block when a page reads weakly (the `tier2_is_weak` test already exists).
- **Thresholding is not the knob on this group.** Sauvola and adaptive Otsu are within noise
  of each other and of Otsu, trading documents both ways. Most of these scans are bilevel
  CCITT fax rasters, already thresholded by the fax machine; Sauvola's case is grey-scale or
  colour scans with show-through, a minority here. Keep it as an option, default Otsu.
- **Upscaling helps dates and totals a little** (+11 dates, +5 totals) at 50% more time and
  with no gain in reconciliation. Worth a second look combined with sparse segmentation on
  the 200-dpi half only; not a default on its own.
- **The render tier did not engage** with `PDFIUM_LIBRARY_PATH` pointing at the library on
  this machine: identical rows to the baseline and the same 24 JBIG2 documents with no
  result. Either the hint is not what the loader reads or the library there is not loadable;
  the JBIG2 route in §9.2 stands, with the pure-Rust decoder looking like the shorter path.

Caveat: these are proxies. "Different value" counts in the diffs (55 totals changed under
sparse) are reads that changed without labels to say which is right; reconciliation is the
only arbiter until the dev sample is labelled (§6.2).

## 9. Open questions for Andrew

1. **How the eye-check happens:** a local browser page (page image beside the pre-filled
   fields, keyboard to confirm and move on, writes the expected files) or a pre-filled file
   per document edited in an editor with the page images open alongside. The page is more
   work and faster to use for 100 documents; the file is an hour of work and needs no
   browser. Either way the page images come from the embedded rasters themselves (the scan is
   the page), so no renderer is needed for scanned documents; a mixed document's native pages
   show their text lines instead.
2. **The JBIG2 route (§5):** PDFium reachable at runtime, or a pure-Rust decoder. The
   `pdfium` run in §7 says what the render tier buys on this machine.
3. Settled: the lexicon work in flight on 2026-11-07 landed as commit 775dbd0, and every §7
   run shares that build, so "today's behaviour" is that commit.

## 10. Builder check

render tier (now §5 and §9.2), the labelling flow (§9.1), what `OcrOptions.languages` meant
(settled in §6.5: extend the existing type, no new field), the language stratification key

build's `scanned` row is read as "not applicable" (decidable, left to the builder).
